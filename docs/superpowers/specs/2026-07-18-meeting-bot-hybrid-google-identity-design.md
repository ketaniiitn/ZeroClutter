# Meeting Bot — Hybrid Google Identity Design

**Date:** 2026-07-18  
**Status:** Approved design; awaiting written-spec review  
**Supersedes identity/join-flow sections of:** `2026-07-17-meeting-bot-google-meet-join-design.md`

## 1. Goal and verified platform constraints

ZeroClutter must join Google Meet calls reliably without purchasing a meeting-bot API subscription.
It must support:

- meetings hosted by personal Gmail accounts;
- meetings hosted by Google Workspace accounts controlled by the user;
- meetings hosted by external organizations, as far as their admission policy permits.

Otter's public documentation states that its Notetaker always joins as an unsigned guest and cannot
sign into a Meet account. Read supports both a traditional guest participant and a newer botless
Google Meet Media API integration. The latter requires Google integration access and consent and does
not appear as a meeting participant.

No client can override a meeting organizer's or Workspace administrator's admission policy. If a
meeting blocks unsigned guests and external Google accounts, ZeroClutter must report that policy
failure accurately; it must not pretend it can bypass it.

## 2. Chosen approach

Use a subscription-free, self-hosted hybrid browser worker:

1. Try an unsigned named-guest join first, matching Otter's documented participant flow.
2. If Meet explicitly blocks unsigned guests or requires a Google account, retry with a dedicated
   ZeroClutter Google account using previously saved Google session state.
3. If the authenticated external account is also blocked, fail with an actionable host-policy reason.

The Google Meet Media API is not part of this implementation because it changes the product from a
visible joining bot to botless capture, requires separate Google integration eligibility and consent,
and is unnecessary for the current join-only scope.

## 3. Identity and credential model

### 3.1 Dedicated account

The authenticated fallback uses a dedicated account such as `zeroclutter.notetaker@gmail.com`, never
the operator's personal Chrome profile.

The account's Google profile name is the visible name in authenticated mode. The per-job
`displayName` remains the visible identity in guest mode.

### 3.2 One-time interactive login

`bot-worker` adds:

```bash
npm run google:login
```

This command:

1. launches headed Playwright Chromium;
2. opens Google's account login page;
3. allows the operator to complete password entry, MFA, CAPTCHA, and security prompts manually;
4. waits until Google login succeeds;
5. saves Playwright `storageState` to `bot-worker/.auth/google-state.json`;
6. writes the file with owner-only permissions where supported.

No Google password, recovery code, or MFA secret is stored in `.env`, source control, or the database.
The storage-state file is a credential and must be protected like a password.

### 3.3 Runtime contexts

Each bot job gets an isolated browser context. Authenticated contexts load
`.auth/google-state.json`; jobs do not launch against a shared personal Chrome user-data directory.
This avoids Chrome profile-lock contention and permits multiple worker jobs without sharing mutable
tabs.

`bot-worker/.auth/` and `.debug/` remain gitignored.

## 4. Configuration

New worker settings:

```dotenv
# guest | account | hybrid
GOOGLE_AUTH_MODE=hybrid

# Generated by npm run google:login
GOOGLE_STORAGE_STATE_PATH=.auth/google-state.json

# Dedicated bot email, used for status/UI only
GOOGLE_BOT_EMAIL=zeroclutter.notetaker@gmail.com
```

Modes:

- `guest`: unsigned named guest only;
- `account`: authenticated context only;
- `hybrid`: guest first, authenticated retry only for a classified guest-policy/sign-in block.

Missing or expired storage state in `hybrid` mode does not prevent the initial guest attempt. If the
fallback is required, the bot fails with a clear instruction to rerun `npm run google:login`.

## 5. Join architecture

The existing backend, BullMQ queue, Redis control channel, Postgres model, worker process, and frontend
remain in place.

The Google Meet code is split into focused units:

- `google-auth.ts`: validates storage state and creates authenticated/anonymous contexts;
- `google-login.ts`: one-time interactive login bootstrap;
- `google-meet-page.ts`: classifies Meet screens and handles interstitials;
- `google-meet.joiner.ts`: orchestrates guest attempt, optional account fallback, admission, and leave;
- `selectors.ts`: central location for Meet selectors and user-visible screen text.

The joiner returns typed failure classifications rather than inferring fallback from arbitrary error
strings:

- `INVALID_OR_ENDED_MEETING`;
- `GUEST_ACCOUNT_REQUIRED`;
- `GUEST_BLOCKED_BY_POLICY`;
- `AUTH_SESSION_MISSING`;
- `AUTH_SESSION_EXPIRED`;
- `EXTERNAL_ACCOUNT_BLOCKED`;
- `JOIN_UI_CHANGED`;
- `ADMISSION_TIMEOUT`;
- `ADMISSION_DENIED`.

## 6. Join flow

### 6.1 Guest attempt

1. Start `JOINING`.
2. Create a fresh anonymous context with fake media devices.
3. Navigate to the Meet URL.
4. Handle cookie and media dialogs, preferring "Continue without microphone and camera."
5. Detect the actual screen:
   - guest lobby: fill the configured display name;
   - direct lobby with join button: continue;
   - sign-in/account-required screen: classify for fallback;
   - invalid, ended, or policy-blocked screen: classify accurately.
6. Ensure microphone and camera are off.
7. Click "Ask to join" or "Join now."
8. Set `WAITING_ADMISSION`; after admission set `IN_CALL`.

### 6.2 Authenticated fallback

In `hybrid` mode, fallback is allowed only for `GUEST_ACCOUNT_REQUIRED` or
`GUEST_BLOCKED_BY_POLICY`.

1. Close the anonymous context.
2. Validate the storage-state file.
3. Create a new context from that state.
4. Navigate to the same Meet URL.
5. If redirected to Google login, classify `AUTH_SESSION_EXPIRED`.
6. Ensure microphone and camera are off.
7. Click "Ask to join" or "Join now."
8. Continue through admission and in-call lifecycle as normal.

No fallback loop is permitted. There is at most one guest attempt and one authenticated attempt.

### 6.3 Leave and cleanup

The existing persisted `leaveRequested` behavior remains authoritative. A leave requested before
either attempt prevents a browser launch; a leave during either attempt closes the active context.
Every success, failure, retry, and shutdown path closes its context/browser exactly once.

## 7. Data and API behavior

No new database model is required. Existing `MeetingBot.botEmail` stores the configured bot email when
authenticated fallback is used.

`statusDetail` reports useful progress/failure details, for example:

- `Joining as guest`;
- `Guest access blocked; retrying with bot account`;
- `Bot Google session expired; run npm run google:login`;
- `Host organization blocks external accounts`;
- `Waiting for host admission`.

Existing API routes and response shapes remain backward-compatible.

The frontend continues polling bot status. It shows the specific `statusDetail` for failed bots and may
show whether the active attempt is `Guest` or `Bot account`; it never exposes storage-state contents.

## 8. Diagnostics

When a Meet screen cannot be classified, the worker saves:

- a screenshot;
- current URL;
- visible page text (bounded);
- sanitized input/button metadata.

Diagnostics go to gitignored `.debug/`. They must redact input values, cookies, authorization headers,
and storage-state data.

## 9. Testing

Automated tests:

- configuration validation for `guest`, `account`, and `hybrid`;
- missing/expired storage-state handling;
- guest success without authenticated retry;
- guest account-required classification followed by one authenticated retry;
- no retry for invalid/ended meetings or unknown UI;
- authenticated redirect to login classified as expired session;
- leave and browser cleanup across both attempts;
- exact status transitions and `statusDetail`;
- debug metadata contains no input values or credentials.

Manual acceptance matrix:

1. Personal Gmail host, guest allowed.
2. Personal Gmail host, signed-in fallback.
3. Workspace host with guest admission enabled.
4. Workspace host requiring signed-in external account.
5. External Workspace blocking guests/external accounts (must fail clearly).
6. Expired Google bot session (must instruct re-login).
7. Host admits, denies, and never responds.
8. Leave requested while pending, joining, and in call.

## 10. Deployment and cost

There is no meeting-bot API subscription. Costs are limited to infrastructure already chosen by the
project (worker compute, Postgres, Redis, and network usage).

Each deployed worker instance receives the storage-state credential through a protected volume or
secret-file mechanism. The file is never baked into an image or committed. Operators rotate the
session by rerunning `npm run google:login`.

## 11. Non-goals

- bypassing Google Workspace administrator or host admission restrictions;
- automated password/MFA/CAPTCHA handling;
- reuse of personal Chrome profiles;
- Google Meet Media API recording;
- recording, transcription, or analysis;
- Zoom and Teams support in this change.
